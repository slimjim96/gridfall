# 03 · Fix32 Arithmetic

All simulation math is `Fix32` — Q16.16 fixed point, backed by an `int`. No `float`, no `double`, ever,
anywhere in `Gridfall.Core`. See [ADR-0002](../../engine-systems/decisions/ADR-0002-fixed-point-arithmetic.md)
for why; this chapter is how.

## The type

```csharp
public readonly struct Fix32 : IEquatable<Fix32>, IComparable<Fix32>
{
    public const int FractionalBits = 16;
    public const int One = 1 << FractionalBits;      // 65536

    public readonly int Raw;                          // the whole value, scaled by 65536

    public static Fix32 FromInt(int v);
    public static Fix32 FromRaw(int raw);
    public static Fix32 FromFraction(int numerator, int denominator);

    public int   ToInt();                             // truncates toward zero
    public int   RoundToInt();
    public float ToFloat();                           // VIEW LAYER ONLY
}
```

| Property | Value |
|---|---|
| Range | ±32,767.99998 |
| Resolution | 1 / 65,536 ≈ 0.0000153 |
| Backing | `int` (32-bit), intermediate products in `long` |

At Gridfall's scale — a cell is `1.0` — the resolution is about 0.015 mm of a tile. Nothing in the game
distinguishes anything that fine.

## Constructing values

```csharp
Fix32 a = Fix32.FromInt(3);                  // 3.0
Fix32 b = Fix32.FromFraction(1, 3);          // 0.333328… — nearest representable
Fix32 c = Fix32.FromRaw(32768);              // 0.5, exactly
```

**`FromFraction`, not a float literal.** There is no `Fix32.FromFloat` in Core and there never will be
— it is the door every determinism bug walks through. The loader in `Content/` converts JSON numbers to
`Fix32` through `FromFraction`, and that conversion is the one and only place a decimal in a data file
becomes a sim value ([Chapter 07](07-content-loading.md)).

## Arithmetic

```csharp
Fix32 sum  = a + b;                    // plain int add
Fix32 prod = a * b;                    // (long)a.Raw * b.Raw >> 16
Fix32 quot = a / b;                    // ((long)a.Raw << 16) / b.Raw
Fix32 neg  = -a;
bool  less = a < b;
```

Add and subtract are exact. Multiply and divide truncate toward zero — **consistently on every
platform**, which is the whole point. `float` rounds to nearest and its behavior across x64/ARM64 and
JIT versions is what we are avoiding.

### Cost

| Operation | Roughly |
|---|---|
| `+ - < >` | one int instruction |
| `*` | 64-bit multiply + shift |
| `/` | 64-bit divide — ~20× a multiply |

Prefer reciprocal-multiply in hot loops. Compute `Fix32 inv = One / n` once outside the loop and
multiply inside it.

## Vectors

```csharp
public readonly struct FixVec2
{
    public readonly Fix32 X, Y;

    public Fix32 LengthSquared();     // exact-ish, no sqrt
    public Fix32 Length();            // FixMath.Sqrt — avoid in hot paths
    public FixVec2 Normalized();      // one Sqrt + two divides — expensive
}
```

**Compare squared distances.** Range checks, target selection, and proximity tests never need a square
root:

```csharp
// good
if (FixVec2.DistanceSquared(tower.Pos, creep.Pos) <= tower.RangeSquared) { … }

// bad — a sqrt per creep per tower per tick, for no gain
if (FixVec2.Distance(tower.Pos, creep.Pos) <= tower.Range) { … }
```

Precompute `RangeSquared` when the tower def is loaded, not per tick.

## Sqrt and trig

`FixMath.Sqrt` is integer Newton–Raphson with a fixed iteration count — identical everywhere by
construction, no platform library involved.

`FixMath.Sin` and `Cos` are **table-based**: 1,024 entries over a quarter turn, linear interpolation
between them, angles as `Fix32` turns (0 → 1 is a full rotation, not radians — no π rounding anywhere).

```csharp
Fix32 s = FixMath.Sin(Fix32.FromFraction(1, 4));   // quarter turn → 1.0
```

If you find yourself needing a transcendental Core does not have, ask whether the algorithm can be
restated without it before adding one. Most of them can.

## Precision, and where it goes wrong

The one real hazard is **accumulation**. Adding a tiny value many times loses what falls below the
resolution, and unlike floats the loss is uniform rather than relative.

```csharp
// BAD — damage-over-time, 0.01 per tick, truncated toward zero each time
creep.Hp -= Fix32.FromFraction(1, 100);

// GOOD — accumulate the fraction, apply whole units
creep.HpFraction += Fix32.FromFraction(1, 100);
if (creep.HpFraction >= Fix32.One) {
    int whole = creep.HpFraction.ToInt();
    creep.Hp -= whole;
    creep.HpFraction -= Fix32.FromInt(whole);
}
```

The rule: **anything applied every tick in small amounts needs an explicit accumulator.** DoT, slow
decay, income drip, regeneration. The accumulator is state, so it goes in the hash
([Chapter 04](04-state-and-entities.md)).

## Overflow

`Fix32` overflows above ±32,768. In debug builds the operators are `checked` and will throw; in release
they wrap silently. Two places to watch:

- **Squared distances.** A 64-cell diagonal squared is ~8,192 — fine. A 64×64 grid is the documented
  cap partly because of this.
- **Damage totals.** Accumulate large sums in `long` or plain `int`, not `Fix32`. Health and gold are
  plain `int` for exactly this reason; only sub-cell positions and rate-like values are `Fix32`.

## The boundary

`ToFloat()` exists, and calling it inside `Gridfall.Core` is a bug. It is there for the view layer,
which converts at the last moment for rendering and interpolation:

```csharp
// godot/  — view side, correct
var world = IsoGrid.GridToWorld(state.CreepCell(i)) + state.CreepOffset(i).ToVector3();
```

A grep for `ToFloat` inside `Gridfall.Core/` should return nothing. Stage 05 checks it.

## Writing tests

```csharp
[Fact] public void Multiply_Truncates_TowardZero() { … }
[Fact] public void Sqrt_MatchesTable_ForAllPerfectSquares() { … }
[Fact] public void DotAccumulator_AppliesExactlyOnePerHundredTicks() { … }
```

Assert on `Raw` values, not on floats. `Assert.Equal(0.5f, x.ToFloat())` reintroduces float comparison
into a test suite whose entire purpose is not having any.
